# 横断分析の手順: Task Contract Prompt は、従来型のプロンプトと比べて何が効くのか（v1.5、実行前に固定）

作成: 2026-11-26。v1〜v4 の実験はすべて終わっており、本分析は既存の成果物の再採点と再分析である（新しい被験エージェントの実行はない）。

## 問い

従来型のプロンプト（B: 短い依頼と、前提を report.md に書く指示）と Task Contract Prompt（TC、TC+、TC+CL）の差を、プロンプトの構成要素に分解する。

## 方法

1. v1〜v4 の全回を、事前登録した隠しテストで要件ごとに採点し直す（`analyze_ladder.py`、出力 `data/ladder_req.csv`）。
2. 同じモデルと課題の層の中で、隣り合う条件を比べる（片側の層別順列検定。共通の層だけを使う）。比べる段は次のとおり。
   1. NOASK − B: 契約の構造、計画、自己テスト（回答なし）
   2. TC/TC+ − NOASK: 質問への回答
   3. TC+ − TC: 値を含む選択肢と1回の聞き返し
   4. TC+CL − TC+: Spec Mode の観点リスト
   5. B-POST − B: 実装後の回答と修正
   6. BALL − B-POST: 前提の全列挙
   7. OFULL − OFILE: 回答者が全文を読む
   8. Spec Mode（TC+、TC+CL）− 事後（B-POST、BALL）: 回答のタイミング
   9. TC 系 − B: 全体
   10. FULL − B: 参考（すべての規則を依頼文に書いた場合）
3. 仕組みの分析: 回答を受けた条件で、各隠し要件が回答に現れたか（`data/surfacing_rules.json` のキーワード規則）と、その要件の合否の関係を集計する。B で通常落ちる要件（B の合格率 50% 未満）に限った集計も示す。
4. キーワード規則の検証: 回答の本文、課題、要件の文面だけを、条件と合否を伏せて独立した判定者に渡し、要件ごとに「回答が伝えたか」を判定させ、キーワード規則との一致率と、判定者の分類での同じ集計を示す。

## 予想（H30〜H32）

- H30: 段1（NOASK − B）は小さく、段2（回答）が最大である。
- H31: 回答に現れた要件の合格率は、現れなかった要件より高い。B で通常落ちる要件で、その差は大きい。
- H32: TC 系と事後確認の差は、回答に現れた要件の割合（surfacing rate）の差で、おおむね説明できる。

## 位置づけ

既存データの事後の分析であり、これまでの事前登録の検定を置き換えない。v1 の TC は v1 の回答（oracle_log.json）、v2 以降は answers.md と answers2.md を回答として使う。
