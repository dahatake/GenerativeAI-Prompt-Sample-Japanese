## 1. 調査結果

作業ディレクトリにあるのは `members.json`（7件）だけです。`solution.py`、テスト、README、依存関係の定義ファイルはありません。

### 確認できた事実
- 各レコードのキーは `id`, `name`, `email`, `updated_at` の4つで、全件共通です。
- `id` は 1〜7 で、すべて異なります。そのため `id` だけをキーにすると重複は0件になります。
- `email` の表記ゆれ:
  - id1 `taro.yamada@...` と id3 `" Taro.Yamada@..."` は、前後の空白と大文字小文字を除けば同じアドレスです。`name` も同じ「山田 太郎」です。
  - id2 `hanako.sato@...` と id6 `HANAKO.SATO@...` は、大文字小文字を除けば同じアドレスです。`name` も同じ「佐藤 花子」です。
- `email` が欠けているレコード: id4 は `""`、id5 は `null` です。
- `updated_at` はすべて ISO 8601 形式で、タイムゾーンはすべて `+09:00` です。重複ペアの新しい方は、id3（3/15、id1 は 1/10）と id2（2/1、id6 は 1/5）です。
- 名前が同じでメールが異なるレコード（同姓同名の別人の可能性があるもの）は、このデータにはありません。

### 仮定（質問で覆らない限りこのまま進めます）
- A1: Python 3、標準ライブラリだけを使います。`dedupe` は JSON を読み込んだ後の `list[dict]` を受け取ります（ファイル入出力は行いません）。
- A2: 返すのは入力の dict そのものです。`email` を正規化した値に書き換えたりはしません。入力リストと dict も変更しません。
- A3: 出力の順序は「各重複グループが最初に現れた位置」の順にします。
- A4: `updated_at` は timezone-aware な datetime として比較します。同時刻の場合は先に現れた方を残します。
- A5: 空のリストを渡されたら空のリストを返します。
- A6: `strip()` 後に空になる email（空白のみ）も「空」とみなし、判定対象外とします。
- A7: `updated_at` は `datetime.fromisoformat` で解釈できる文字列（末尾 `Z` は UTC として扱う）とし、比較は時刻として行います。

- 想定されるデータ量（O(n) の実装で十分かどうか）。今回は質問しません。

## 2. 質問（最大3問）

**Q1. 重複判定キー**
- (a) 推奨: `email` を正規化した値（`strip()` してから `casefold()`）
- (b) `name` と正規化した `email` の組み合わせ
- (c) `name` だけ
- (d) `id`（この場合、今のデータでは重複0件になります）

**Q2. 残すレコード**
- (a) 推奨: `updated_at` が最も新しいもの。フィールドのマージはしません。
- (b) 先に現れたもの
- (c) 項目ごとにマージする（空でない値と新しい値を優先する）

**Q3. `email` が空または `null` のレコード**
- (a) 推奨: 重複判定から外し、すべてそのまま残します。
- (b) 代わりに `name` で重複判定します（同姓同名の別人を誤って統合するおそれがあります）。
- (c) 出力から除外します。
