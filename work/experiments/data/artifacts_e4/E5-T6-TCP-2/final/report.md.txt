補足（DoD 5）: 期待値は、回答どおりの規則で私が手計算した参照値です。テストはその参照値との一致を見ています。経理担当者などが別途計算した正解値は使っていないため、金額が業務上正しいかは人間の確認を推奨します。結果は、Spec Mode 時点の按分方式による値とも一致しました。現データでは両方式の差が出ないためです。区分ごとの切り捨てに従っていることは、合成データのテストで確認しています（全体に 5% を掛けると 1 円になるケースで、0 円になる）。

## 採用した仮定・規則の一覧

| ID | 内容 | 根拠 |
|---|---|---|
| Q1 | `ordered_at`(UTC) を JST(UTC+9) の日付に変換し、計上月と単価適用日の両方を判定する | 回答 |
| Q2/T2 | `gold` は税率区分ごとの小計にそれぞれ 5% を掛けて切り捨てる。`discount` はその合計。`standard` は 0 | 回答 |
| Q3 | 請求対象は `completed`/`shipped`。`cancelled`/`returned` は除外 | 回答 |
| T1 | `category == food` は 8%、それ以外は 10% | 回答（承認） |
| T3 | 請求書ごと・税率区分ごとに `floor((区分小計 − 区分値引き) × 税率)` を計算して合計する | 回答（承認） |
| T4 | `amount = qty × unit_price`、`subtotal = Σamount`、`total = subtotal − discount + tax`。整数演算のみ | 契約 |
| T5 | 単価は JST の注文日時点で `effective_from <= 注文日` を満たす最新のもの | 回答（承認） |
| T6 | 1顧客×1か月で1請求書。請求対象行がない顧客には請求書を作らない | 回答（承認） |
| T7 | `invoice_id = INV-YYYYMM-NNNN`。その月の請求書を customer_id 昇順に並べ、0001 から連番 | 回答 |
| T8 | 請求書は customer_id 昇順。lines は JST の ordered_at 昇順（同時刻は order_id 昇順） | 回答（承認） |
| T9 | month が `YYYY-MM` でない場合、未知の customer/sku、有効な単価がない場合は ValueError。注文のない月は `[]`（CLI はヘッダーのみ出力） | 指定なし → 推奨案 |
| T10 | CSV は UTF-8（BOM なし）、ヘッダー付き、`csv` モジュールの標準改行 | 指定なし → 推奨案 |
| T11 | Python 標準ライブラリのみ使用。入力 CSV は BOM 付きでも読める（`utf-8-sig`） | 契約 |

## 人間の確認が必要な点
- DoD 5 の期待値（特に gold 顧客 C001・C003 の値引きと税額）を、業務上の正解と照合してください。
- 番号 `NNNN` は「その月・その data_dir で生成した請求書の連番」です。顧客の増減で番号が変わります。請求書の再発行時に番号を固定したい場合は、別途ルールが必要です。
