## 2. 確認できた事実

- F1: ファイルは UTF-8（BOM なし）、改行 CRLF、カンマ区切り、ヘッダ `order_id,ordered_at,amount_incl_tax,status`。引用符・空行・欠損値はない。
- F2: `ordered_at` は ISO 8601 の UTC（末尾 `Z`）。
- F3: 金額列は `amount_incl_tax`（列名から**税込**）。値はすべて整数で、全件 11 の倍数（税率 10% の税込額と整合）。
- F4: `status` は `completed`（8 件）と `cancelled`（2 件: A-1003, A-1007）の 2 種類。
- F5: 負の金額が 1 件（A-1006, -1100, completed）。返品・返金と推測されるが根拠はない。
- F6: データ期間は 2026-01〜2026-04 で、**2026-03 のデータは 0 件**。
- F7: UTC と JST で月が変わる行が 2 件（A-1004: 1月→2月、A-1010: 4月→5月）。タイムゾーンの選び方で結果が変わる。
- F8: order_id の重複はない。
- F9: 既存の `solution.py`・テスト・依存定義はない。Python は利用できる。

## 3. 仮定（回答がなければこの前提で進める）

- A1: 実装は Python 標準ライブラリ（`csv`, `datetime`, `zoneinfo`）だけを使う。pandas などは使わない。
- A2: 戻り値の dict にはデータのある月だけを入れる（2026-03 のような 0 件の月は含めない）。キーは `"YYYY-MM"` 形式で、昇順に挿入する。
- A3: 金額は `int` で返し、浮動小数は使わない。
- A4: `path` は `str` または `os.PathLike` を受け取る。読み込みは `encoding="utf-8-sig"`, `newline=""` とする（BOM ありでも読める）。
- A5: 列の順序には依存せず、ヘッダ名で列を参照する。
- A6: 不正な行（日付や金額が解析できない行）は黙って捨てずに例外を送出する。現データにはそのような行はない。
- A7: 対象は `sales.csv` と同じスキーマの CSV。

## 4. 不足情報

## 5. 質問（最大3問。回答で実装が変わり、外れた場合の手戻りが大きいもの）

### Q1. 月の境界はどのタイムゾーンで判定しますか？
- (a) **Asia/Tokyo（JST）で月を判定する** ← **推奨既定案**（日本の営業月として扱うのが一般的なため）
- (b) UTC のまま（`ordered_at` の先頭 7 文字）で判定する
- (c) その他のタイムゾーン（指定してください）

影響: A-1004 と A-1010 の所属月が変わります。(a) を選ぶと 2026-05 が出力に現れます。

### Q2. どの行を集計対象にしますか？
- (a) **`status == "completed"` だけを集計し、負の金額（返金）は差し引く（ネット売上）** ← **推奨既定案**
- (b) completed だけを集計し、負の金額は除外する（総売上）
- (c) status に関係なく全行を合算する

### Q3. 金額は何を基準に集計しますか？
- (a) **`amount_incl_tax`（税込）をそのまま合算する** ← **推奨既定案**（データにある値をそのまま使える）
- (b) 税抜（10% で割り戻す）で集計する。この場合は端数処理（行ごとか月合計か、切り捨てか四捨五入か）も指定してください。

## 6. Task Contract（案）

### Outcome
`solution.py` に `monthly_sales(path) -> dict[str, int]` を実装する。この関数は `path` の CSV を読み、Q1〜Q3 で決めた規則に従って売上を月ごとに合計し、`{"YYYY-MM": 金額(int)}` を返す。

### Scope / Out of scope
- Scope: `solution.py` の新規作成（`monthly_sales` 関数と必要な補助関数）。動作確認用のテスト（例: `test_solution.py`、標準ライブラリの `unittest`）の追加。
- Out of scope: `sales.csv` の変更、CLI・ファイル出力・グラフ化、外部ライブラリの導入、`sales.csv` と異なるスキーマへの対応、通貨換算、作業ディレクトリ外の操作。

### Data sources
- `sales.csv`（作業ディレクトリ内）。使う列: `ordered_at`（UTC の ISO 8601）、`amount_incl_tax`（int）、`status`。
- `order_id` は集計には使わない。

### Constraints
- Python 3（標準ライブラリのみ。JST にする場合は `zoneinfo`。Windows で tzdata がない環境に備え、固定オフセット `timezone(timedelta(hours=9))` を使ってもよい。JST には夏時間がないため結果は同じ）。
- 戻り値の値は `int`。キーは `"YYYY-MM"`（ゼロ埋め 2 桁の月）。
- 作業ディレクトリの外のファイルは読み書きしない。
- 入力ファイルを変更しない（読み取り専用）。

### Definition of Done（検証できる条件）
1. `from solution import monthly_sales` が成功する。
2. `monthly_sales("sales.csv")` が、確定した規則に対応する次の期待値と**完全一致**する（`==` で比較）。

   | 規則 | 期待値 |

   | Q1=b UTC, Q2=a, Q3=a | `{"2026-01": 19800, "2026-02": 7700, "2026-04": 26400}` |

   その他の組み合わせを選んだ場合は、契約の確定時に期待値を再計算して記載する。
3. すべての値が `int` 型で、すべてのキーが正規表現 `^\d{4}-\d{2}$` に一致する。
4. 境界ケースのテストに合格する。
   - 月末の UTC 深夜の注文（A-1004 型）が、選んだタイムゾーンの月に入る。
   - cancelled の行が Q2 の規則どおりに扱われる。
   - 負の金額が Q2 の規則どおりに扱われる。
   - 0 件の月（2026-03）が A2 のとおり出力に含まれない。
   - BOM 付き CSV や、列の順序が異なる CSV でも同じ結果になる。
5. `python -m unittest` がすべて成功する。
