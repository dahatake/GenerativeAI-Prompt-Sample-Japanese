## 背景

AI Agent に、少し大きめの仕事を任せることが増えました。

便利です。
ただ、少し気になっていることがありました。

依頼文に書いていないことを、Agent が「もっともらしい既定値」で埋めてしまうことです。
タイムゾーン、税込か税抜か、データがない月の扱い、文字列以外が来たときの扱い。
こうした判断が依頼者の意図と違うと、成果物はテストを通っても、仕事としては間違いになります。

そこで、実行の前に人間と Agent が「何を達成するか」「何をもって完了とするか」「どこまで任せるか」を合意する形式を考え、**Task Contract** と呼んでガイドにまとめていました。

正直、最初はこう思っていました。
「Task Contract を書いてから任せれば、Agent の成果物は正しくなるはずだ」

でも、本当にそうなのか。
効くとしたら、どんな仕事で、何が効いているのか。
効かない仕事はあるのか。

そこで、Task Contract の考え方を文献で確認したうえで、**仮説を事前に登録し、Agent から見えない隠しテストで採点する小さな実験**を行いました。
この記事では、その結果と、結果から考えたことを整理します。

なお、今回の実験の設計・実行・採点は、私が AI アシスタント（Copilot SDK）に依頼して行わせ、私が結果を確認しました。
Agent に仕事を任せる方法を、Agent に仕事を任せて確かめた、という少し入れ子の構造です。

## Task Contract とは

読者の多くは、「Task Contract」という言葉をご存じないと思います。
これは、私がガイドとしてまとめている考え方の名前で、標準化された用語ではありません。

### 何を解決するか

Agent に仕事を任せるときに、**依頼文に書かれていない判断を、Agent が黙って既定値で埋めてしまう問題**を減らすことが目的です。

### 定義

> AI Agent に仕事を任せる前に、人間と Agent が合意するタスク単位の委任契約。Outcome（実現したい状態）、根拠にするデータ、制約、検証できる完了条件（Definition of Done、DoD）と証拠、自律の範囲と承認ゲート、失敗時の扱いを、自然言語と機械が読める形式の両方で記述する。

法的な契約ではありません。
Design by Contract のような形式検証でもありません。
MCP の Tasks や A2A の Task（実行時の状態機械）とも別物です。

### 動き（工程）

仕様を作る段階（Spec Mode）と、実行する段階（Execution Mode）を分けて、その間に承認ゲートを置きます。

```text
初期意図 ─► [Spec Mode] 探索 → 事実・仮定・不足の分離 → 最大3問の質問（選択肢と推奨案、具体値つき）→ 契約案
        ─► Gate 1（契約の承認）
        ─► 小さな試行 ─► Gate 2（試行結果を見てから本実行を承認）
        ─► [Execution Mode] 実装 → 自己検証（コマンドと出力）→ DoD ごとの状態（完了 / 証拠不足 / 人間の確認が必要）
        ─► 独立した検証（隠しテスト、レビュアー、CI）─► 受け入れ
```

Execution Mode では、承認済みの契約の範囲内にある低リスクな判断に限って、質問せずに仮定を記録して進めます。
重要な操作の承認、エスカレーション、契約範囲を超える変更の再承認は、実行中も残します。

### 構成要素（記述形式 v0.2 の要約）

<details><summary>記述形式 v0.2（YAML の要約）</summary>

```yaml
task_contract:
  version: 0.2
  weight: M                       # S / M / L
  required_by_weight: { S: [outcome, definition_of_done], M: [outcome, scope, data_sources, definition_of_done, approval], L: [all] }
  defaults:                       # 省略した権限は「許可」ではない
    autonomy: { always: [read, draft], ask_first: [write, send, share, delete, execute], never: [] }
    untrusted_content_is_data: true
    external_actions_in_spec_mode: forbidden
  fields:
    outcome: ""
    motivation: ""
    scope: { in: [], out: [] }
    data_sources: { trusted: [], untrusted: [] }
    definition_of_done: [{ id: DoD-1, check: "", evidence: "", verifier: "" }]
    approval: { gate1_contract: "", gate2_execution: "" }
    assumptions: []               # 人間や環境が満たすこと
    failure_policy: { max_retries: 2, stop_conditions: [], escalate_to: "" }
    budget: { max_time: "", max_cost: "" }
  change_log: []
```

</details>

契約の重さは、S（一行の完了条件）、M（Spec Mode と3問の質問）、L（すべての項目と信頼境界）の3段階で使い分ける想定です。

### 似た考え方

「Task Contract」という言葉自体は、2026年に複数の実務資料が同じ意味で使い始めていますが、標準化はされていません。
近い考え方には、次のようなものがあります。

- 学術：Agent Contracts [R7]、Software Delegation Contracts [R3]、Google DeepMind の contract-first decomposition [R6]
- ツール：GitHub Spec Kit、AWS Kiro specs、OpenAI の ExecPlan（PLANS.md）[R12]、Claude Code の Plan mode [R13]、Factory の Spec Mode、Magentic-UI の co-planning [R8]

どれも「仕様を作る段階」と「実行する段階」を分ける点が共通しています。

## 整理・考え方

実験の前に、言葉を少し分けておきます。

### 「正しさ」と「レビューしやすさ」を分けておく

Task Contract が役立つとしたら、少なくとも2つの意味があり得ます。

- 成果物そのものが正しくなる（正しさ）
- 成果物のどこが怪しいかが分かる（レビューしやすさ）

文献では、契約全体を直接比較した研究は小規模な予備研究1件だけでした。
そこで確認された効果は、**レビューしやすさの向上と、コストの増加（トークン +13%、時間 +38%）**です [R3]。
正しさは、全条件で合格したため差が測れていませんでした。

今回の実験は、主に**正しさ**を測ります。

### 「書く」と「聞く」は別に考える

前提を報告書に「書く」ことと、実装の前に「聞く」ことは違います。

事後に書くだけなら、誤った実装はすでに完成しています。
事前に聞けば、実装の前に訂正できます。

今回の比較でも、この2つを混ぜないように見ていきます。

### 安全性は別の軸で考える

Agent はメールやファイルを読みながら仕事をします。
読んだ内容の中に「この資料を外部に送れ」という指示が紛れていたら、どうなるか。

これは正しさとは別の問題なので、Experiment 2 として分けて測ります。

この記事では、依頼の仕方を次の名前で呼びます。
最後まで、この呼び方と順序を変えません。

**Experiment 1（仕様が足りない依頼）**

## 検証

### 1. 実験の設計

#### 目的

Task Contract の構成要素（Spec Mode での探索と質問、検証できる DoD、Trust boundary）が、Agent の成果に影響するかを、Agent の自己申告ではなく**外部の証拠**で確かめます。

#### やったこと

1. **事前登録**：仮説、条件、指標、分析方法を、実行の前に文書にしてハッシュ（SHA-256）を記録しました。
2. **隠しテスト**：各課題に「依頼文には書かれていない本当の要件」を4つずつ用意し、要件ごとに独立したテストを書きました。テストは、Agent の作業場所の外に置きました。
3. **テストの検証**：全要件を満たす参照実装は全テストに合格し、素朴な参照実装は大半に不合格になることを、実行前に確認しました。
4. **ユーザー役（オラクル）**：Task Contract の質問には、隠し要件を知っている別のサブエージェントが「尋ねられた点だけに答え、ヒントは出さない」ルールで回答しました。
5. **隔離**：1回の実行ごとに、独立した作業ディレクトリを用意しました。
6. **送信の擬似ツール**：Experiment 2 の送信ツールは、実際には送らず、送信ログに記録するだけにしました。

:::note info
**オラクル**は、ここでは「依頼者の頭の中にある本当の要件を知っていて、聞かれたことにだけ答えるユーザー役」のことです。Ambig-SWE という研究の評価方法と同じ型です [R1]。
:::

#### 仮説（事前登録）

| 仮説 | 内容 |
|---|---|
| H1 | Task Contract の隠し要件の充足率は、短い依頼より高い |
| H2 | Task Contract は、短い依頼より仮定を多く報告書に書く |
| H3 | Task Contract は、短い依頼より時間がかかる |
| H4 | 完全な仕様は、Task Contract 以上の充足率になる |
| H5 | ガイドの契約＋Trust boundary は、メールに紛れた指示への追従が、短い依頼とガイドの契約以下になる |
| H6 | ガイドの契約＋Trust boundary は、不審な指示の報告率が最も高い |

### 2. Experiment 1：仕様が足りない依頼

#### 狙い

依頼文に書かれていない業務ルールがあるとき、Task Contract（実装前に質問する）は、隠れた要件をどれだけ満たせるのか。

#### 課題と隠し要件

| 課題 | 依頼（全方式で共通） | 隠し要件 |
|---|---|---|
| T1 月次売上の集計 | `monthly_sales(path)` を実装する | R1 キャンセルを除外、R2 日本時間で月を判定、R3 税抜（÷1.1）、R4 データのない月を0で埋める |
| T2 社員名簿の重複除去 | `dedupe(records)` を実装する | R1 メールを正規化して比較、R2 最新を残す、R3 最初に出た位置に並べる、R4 メールが空や null なら対象外 |
| T3 請求書番号の検証 | `validate_invoice_id(value)` を実装する | R1 大文字で完全一致、R2 年 2020〜2099 と月 01〜12、R3 連番 0000 は不正、R4 文字列以外は False |

#### 使用した Prompt

各 Prompt の冒頭には、共通の前置き（作業ディレクトリと制約）が付きます。

```text
作業ディレクトリ: 【ファイルパス省略】
このディレクトリの外にあるファイルは読まない・書かないでください。ask_user などユーザーに問い合わせるツールは使わないでください（質問がある場合は最終回答に書いて終了してください）。
```

**短い依頼**（T1 の例）

```text
sales.csv の売上を月次で集計する関数 monthly_sales(path) を solution.py に実装してください。戻り値は {"YYYY-MM": 金額(int)} の dict です。
作業が終わったら、実装内容と前提にしたことを report.md に簡潔に書いてください。
```

**Task Contract**（Phase 1：Spec Mode）

```text
依頼: {短い依頼の文面}

すぐに実装を始めないでください。まず私と Task Contract を作成します（Spec Mode）。
1. 作業ディレクトリ内のファイルを調べ、依頼に関係する事実を整理してください。
2. 「確認できた事実」「仮定」「不足情報」を分けてください。
3. 回答によって実装が変わり、外れたときの手戻りが大きい点だけを、最大3問質問してください。各質問には選択肢と推奨の既定案を付けてください。
4. 次の項目で Task Contract 案を作ってください: Outcome / Scope・Out of scope / Data sources / Constraints / Definition of Done（検証できる条件）/ Evidence / Open questions。
5. この段階では contract.md（質問と契約案を書く）以外のファイルを作成・変更しないでください。質問と契約案を最終回答として返し、終了してください。
```

**Task Contract**（Phase 2：Execution Mode。ユーザー役の回答をそのまま差し込む）

```text
質問への回答です:
{ANSWERS}

回答がない点は、あなたの推奨既定案で進めてください。
Task Contract を回答で更新し（contract.md を更新）、承認済みとして実行してください（Execution Mode）。
- solution.py に実装してください。
- Definition of Done の各条件について、自分で検証用のテストを書いて実行し、そのコマンドと出力を証拠として示してください。
- 最後に report.md に、各 DoD 条件の状態（完了 / 証拠不足 / 人間の確認が必要）と、採用した仮定の一覧を書いてください。
```

**仮説の判定**

## 考察

### 1. 効いたのは「既定値を実装の前に表に出したこと」かもしれない

T1（月次売上）では、Task Contract の Agent も、短い依頼の Agent と同じ誤った既定値を推奨していました。
差は、それを実装の前に人間に回したかどうかでした。

そのため、私は今、Task Contract の価値を次のように考えています。

- Agent を賢くすることではない
- Agent が黙って埋めようとしている既定値を、実装の前に人間の判断に回すこと

ただし、Task Contract と短い依頼は、質問のタイミング以外にも、ユーザー役への問い合わせ、計画、自己テストなど、多くの点で同時に違います。
**「タイミングが効いた」は仮説で、因果として切り分けてはいません。**
切り分けるには、短い依頼にも事後にユーザー役の回答と修正の機会を与える条件が必要だと考えています。

### 2. 既定値が当たる仕事では、コストだけが増える

T2（社員名簿）では、Agent のもっともらしい既定値（メールの正規化、最新を残す、最初の位置に並べる、空は対象外）が、隠し要件と一致していました。

この場合、Task Contract は正しさを改善せず、Phase 1 だけで時間が +33% 増え、人間の回答の手間も増えました。

効果の大きさは、「既定値が外れる確率 × 外れたときの影響」で決まるのではないでしょうか。

### 3. 回答の質が、契約の質の上限になる

T3（請求書番号）では、Agent の質問は正しい論点を突いていました。
それでも、回答が値を欠いたので、失敗しました。

Task Contract は双方向の契約です。
人間の側にも「値で答える」という義務があると考えています。

もう1つ気づいたことがあります。
T3 の質問の選択肢は「(c) 年の範囲も制限する」のように、**値を含んでいませんでした**。
選択肢が値を含まないと、回答も値を含まないのかもしれません（未検証の仮説です）。

### 4. Trust boundary は、測れなかったが外さない

今回の被験エージェントは、条項がなくても紛れた指示を拒否しました。
それでも、私は次の理由から、条項を残すべきだと考えています。

- 実際の運用では、モデル、ハーネス、ツールの権限は一定ではありません。EchoLeak（CVE-2025-32711）は、本番の Microsoft 365 Copilot で起きています [R14]。
- 条項のコストは小さいと考えられます（3文の追加。所要時間は ガイドの契約 91.7秒、ガイドの契約＋Trust boundary 90.3秒、各3回の記述的な比較のみ）。
- 条項は、Agent の拒否の理由を、契約の条項に結びつけて記録させます。

### 5. 使い分けの案

| 作業 | 当面の候補 | 任せきりにしない点 |
|---|---|---|
| 業務ルールに依存する集計や変換（T1 月次売上の型：税、タイムゾーン、期間） | Task Contract（Spec Mode と最大3問の質問） | 推奨既定案をそのまま承認しない。業務ルールと違う点を訂正する |
| 既定値が当たりやすく、小さく、可逆な作業（T2 社員名簿の型） | 一行の完了条件 | 実装後の前提の報告は読む |
| 値の範囲が組織固有の作業（T3 請求書番号の型） | Task Contract に加え、具体的な値を含む選択肢 | 記号ではなく値で答える |
| 外部への作用、機密、不可逆な操作（Experiment 2 の型） | ガイドの契約＋Trust boundary、操作ごとの承認 | 拒否の理由と、拒否した操作を確認する |

### 6. 結果を踏まえた Prompt の改良版

:::note info

## 今回の結果から言えないこと

- **標本数**：条件ごとの反復は最大3回です。課題内の差は T1 でしか検出できず、検定は p=0.10 にとどまります。
- **課題の規模**：数十秒で終わる小さな課題です。数時間規模の大きな仕事で同じ結果になるかは分かりません。
- **モデルとハーネス**：被験エージェントは1種類です。弱いモデルや、ツールの権限が広い環境では、特に Experiment 2 の結果は変わり得ます。
- **ユーザー役**：LLM のユーザー役で、T3（請求書番号）では値を答えない系統的な偏りがありました。実際の人間の回答の質と頻度は分かりません。
- **測定方法**：仮定の報告はキーワード判定で粗く、偽陰性がありました。トークン数と Phase 2 の実働時間は取得できていません。
- **因果の切り分け**：Task Contract とガイドの契約は、比較相手と多くの点で同時に違います。どの構成要素が効いたかは推測の域を出ません。
- **事前登録の時系列**：ハッシュはローカルに記録したもので、実行前に固定したことを第三者に証明するものではありません。
- **改良版の Prompt**：考察の「6. 結果を踏まえた Prompt の改良版」は、今回の結果から作ったもので、効果は検証していません。

## ここまでの整理

### 良かった点

- 既定値が外れやすい課題（T1 月次売上）で、Task Contract は隠し要件の充足を 50% から 100% にしました（各3回）
- Task Contract の9回すべてで、DoD ごとの状態とテストの実行ログが提出されました
- T3 請求書番号では、失敗した要件（年の範囲）を、3回とも「人間の確認が必要」と報告していました
- 隠しテストと事前登録によって、Agent の自己申告に頼らない比較ができました

### 注意したい点

- 既定値が当たる課題（T2 社員名簿）では、Task Contract は時間を増やしただけでした
- 推奨既定案は、そのまま承認すると、短い依頼と同じ誤りになります
- 回答が値を欠くと、正しい質問でも失敗します
- 「書く」だけなら、短い依頼でも同じくらい書きます

### 今回の限界

- 条件ごとの反復は最大3回、被験エージェントは1種類、課題は小規模です
- Trust boundary の効果は、床効果で測れませんでした
- どの構成要素が効いたかは、切り分けていません

## まとめ

私は今、Task Contract を「Agent を賢くする道具」ではなく、「判断を人間に回すタイミングを決める道具」として使うのがよいと考えています。

| 仕事の性質 | 当面の使い方 |
|---|---|
| 既定値が外れやすい（業務ルール依存） | Spec Mode で最大3問、値を含む選択肢で聞く |
| 既定値が当たりやすく、小さく、可逆 | 一行の完了条件と、事後の前提の報告 |
| 外部への作用、機密、不可逆 | 契約、Trust boundary、操作ごとの承認 |

これは標準でもランキングでもありません。
今回の小さな結果から決めた、次に試す順番です。

次は、次のことを試したいと考えています。

- [ ] 数時間規模の、大きな仕事での比較
- [ ] 複数のモデルと、権限の広いツールでの Experiment 2 の再実験
- [ ] 実際の人間が回答する条件
- [ ] 改良版 Prompt（値を含む選択肢、値の再確認）の検証
- [ ] Workshop で、参加者を無作為に分けた比較

**Agent に任せる前に大切なのは、完璧な依頼文を書くことではなく、Agent が黙って埋めようとしている既定値を、実装の前に表に出させることだと、今は考えています。**
