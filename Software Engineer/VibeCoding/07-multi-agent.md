# 第 7 章 複数 Coding Agent の並列開発

**ゴール**: 複数の Agent を同時に動かし、衝突させずに機能を並列実装して統合する。

## 7.1 講義: 並列化の原則

| 原則 | 説明 |
|---|---|
| **作業ディレクトリを分離** | 同一ワーキングツリーを複数 Agent が触ると破綻する。`git worktree` かクラウド Agent（別ブランチ/別環境）を使う |
| **1 Agent = 1 Issue = 1 ブランチ = 1 PR** | 追跡・レビュー・ロールバックの単位を揃える |
| **契約を先に固定** | 並列の前に Spec / openapi / DB スキーマ方針を確定し、共有ファイルの衝突を最小化 |
| **所有権を分ける** | 各 Agent が触ってよいディレクトリを明示（例: A は `comments/`、B は `labels/`） |
| **統合は人間が主導** | マージ順序を決め、衝突は 1 つずつ解消。CI を必須ゲートに |
| **並列度は人間のレビュー容量以内** | 目安 2〜4。レビューが詰まるなら増やさない |

### 並列に向く / 向かない作業

| 向く | 向かない |
|---|---|
| 独立した機能追加、テスト拡充、ドキュメント、調査・PoC、定型リファクタ | 同一ファイルを大きく変更する作業、スキーマの根幹変更、未確定の設計 |

## 7.2 並列パターン

| パターン | 構成 | 使いどころ |
|---|---|---|
| A. **機能分割** | Agent ごとに別機能（S-005 / S-006 / S-009） | 最も基本。本章のメイン |
| B. **レイヤ分割** | API 担当 / UI 担当 / テスト担当 / インフラ担当 | 契約(openapi)が固まっている時 |
| C. **役割分割** | 実装 Agent + レビュー Agent + テスト Agent | 品質向上。別モデルでクロスレビュー |
| D. **競争（比較）** | 同じ課題を別 Agent/別モデルで実装し、良い方を採用 | 設計の探索、難所 |
| E. **非同期委任** | Issue をクラウド Agent に割り当て、PR で受領 | 手元を空けたい時 |

## 7.3 ハンズオン A: 事前準備 — 衝突しにくい土台作り（30 分）

```text
並列開発の前提を整える提案をして(変更はしない): 共有されやすいファイル(ルーティング登録,
スキーマ定義, UI のナビゲーション等)を特定し、機能ごとに追加できるプラグイン的構造
(例: routes/index.ts は自動登録, マイグレーションは連番ではなくタイムスタンプ)に
するためのリファクタ計画を出して。
```

承認後、**先に単独でリファクタを main に入れる**（並列開始前の下ごしらえ）。

- マイグレーション名は連番でなくタイムスタンプ（番号衝突の回避）
- `AGENTS.md` に「共有ファイルの変更は最小限。触る場合は PR 説明に明記」を追記

## 7.4 ハンズオン B: ローカルで 3 Agent を並列（60 分）

### Step 1: Issue と Spec を用意

S-005（ラベル等）/ S-006（コメント）/ S-009（監査ログ）を Issue 化し、各 Spec を main に入れる。

```powershell
gh issue create --title "S-006 コメント機能" --body "docs/spec/S-006-comments.md に従い実装。受入基準を満たすこと"
```

### Step 2: worktree で作業ディレクトリを分離

```powershell
git worktree add ..\taskboard-s005 -b feat/s005-labels
git worktree add ..\taskboard-s006 -b feat/s006-comments
git worktree add ..\taskboard-s009 -b feat/s009-audit
```

### Step 3: ターミナル/ウィンドウごとに Agent を起動

各ディレクトリで別の Agent セッション（同種でも異種でも可）を起動し、同一テンプレで指示:

```text
あなたは feat/s006-comments ブランチ担当です。このディレクトリのみ変更してください。
タスク: docs/spec/S-006-comments.md を実装(AGENTS.md の規約に従う)。
手順: 1)Plan を提示し承認待ち 2)テスト先行 3)実装 4)lint/typecheck/test 5)コミット
制約: 他機能(S-005, S-009)のファイルは触らない。共有ファイルを変更する場合は理由を列挙。
完了時: 変更ファイル一覧・実行結果・未解決事項を要約。push は私が指示するまでしない。
```

> **ポート/DB の衝突に注意**: 各 worktree で `PORT` と DB 名（例: `taskboard_s006`）を変え、`.env` を別にする。Docker Compose のプロジェクト名（`-p`）も分ける。

### Step 4: 人間の役割（オーケストレーション）

| やること | 内容 |
|---|---|
| 進捗確認 | 各 Agent の Plan を先にレビュー（ここで衝突の芽を摘む） |
| 割り込み | 方向がズレたら即停止し、Spec/指示を直して再開 |
| 記録 | どの Agent がどの Issue を担当し、状態がどうか表で管理 |

## 7.5 ハンズオン C: 統合（40 分）

1. 各ブランチを push し PR を作成 → CI を通す
2. **マージ順序**を決める（依存が少ない/影響が小さい順）
3. 2 本目以降は main を取り込み、衝突を解消:

```text
feat/s006-comments に最新 main をマージしたところ、以下のファイルで衝突しています。
両方の意図(S-005 と S-006 の Spec 参照)を保つ形で解消して、全テストを実行して。
解消方針を先に説明してから変更すること。
```

4. 統合後に **E2E / 全テスト** を実行し、dev へデプロイして画面確認

## 7.6 ハンズオン D: クラウド Agent への非同期委任（30 分）

```powershell
gh issue create --title "S-010 ページング" --body "docs/spec/S-010-paging.md に従い実装。完了の定義は AGENTS.md 参照" --assignee "@copilot"
```

（アサイン方法はお使いの Agent/プランに依存。実施時に公式ドキュメントを確認）

- Agent が作成した PR を、**人間の PR と同じ基準**でレビュー（CI・DoD・セキュリティ）
- レビューコメントで修正を依頼し、反復する
- 手元では別の作業（第 7.4 の並列）を同時に進める

## 7.7 ハンズオン E: 役割分担（実装 + レビュー + テスト）（30 分）

| 役割 | 指示の要点 |
|---|---|
| 実装 Agent | Spec から実装。テストを通す |
| レビュー Agent（別モデル推奨） | 読み取り専用。仕様逸脱・脆弱性・保守性を指摘 |
| テスト Agent | 実装を見ずに Spec のみからテスト設計（独立性を確保） |

テスト Agent の指示例:

```text
S-006 の受け入れ基準だけを根拠に、実装コードを読まずに E2E/API テストを作成して。
実行して失敗した場合は原因を報告(実装は直さない)。
```

## 7.8 失敗パターンと対策

| 症状 | 原因 | 対策 |
|---|---|---|
| マージ衝突が多発 | 共有ファイル/スキーマが集中 | 7.3 の構造化、所有権の明示、頻繁に main を取り込む |
| Agent 同士が矛盾した設計 | Spec/契約が未確定 | 並列前に Spec と openapi を固める。設計は人間が決める |
| レビューが追いつかない | 並列度過多 | 2 つまでに絞る。PR を小さく |
| 同一 DB/ポート使用で不安定 | 環境の共有 | worktree ごとに PORT/DB/Compose プロジェクトを分離 |
| コスト・クォータ超過 | 無制限な並列実行 | 同時実行数・トークン予算を決め、上限を設定 |
| 暴走・想定外の操作 | 権限が広すぎる | 最小権限、承認制（破壊的コマンド・push・デプロイは承認必須）、本番資格情報を渡さない |

## 7.9 後片付け

```powershell
git worktree remove ..\taskboard-s006
git branch -d feat/s006-comments
git worktree prune
```

## 動作確認で判明した注意点(実機検証済み)

実際に 2 つのエージェントを別 worktree で並行実行し(S-005 と S-006)、7.4 のテンプレートに沿って「計画 → テスト先行 → 実装 → コミット」で完了した。

- 各 worktree で `npm ci` を実行し、**PORT と DB をそれぞれ分ける**(例: `taskboard_s005`, `taskboard_s006`)。PostgreSQL の契約テストは TRUNCATE するため、DB 共有だと並行実行が壊れる。
- マージでは `app.ts`、リポジトリ実装、`repositories.test.ts`、`openapi.yaml` が衝突した。
- **意味的な衝突**: git が検知しないものがマージ後のテストで初めて見つかった(S-005 の `TRUNCATE task_labels, tasks` が S-006 の comments の外部キーと衝突 → `TRUNCATE task_labels, comments, tasks` に修正)。**マージごとに PostgreSQL を含む全テストを実行する**。
- `openapi.yaml` を手で衝突解決すると重複キー(duplicated mapping key)になりやすい。マージ後に `npm run gen:api` を実行して検証する。
- エージェントに「`apps/web` を触らない」と制約すると守られるが、その場合 `gen:api` はマージ後に実行する必要がある。
- 同じタイムスタンプ接頭辞でも名前が違えば順序は保たれたが、衝突を避けるため機能ごとに異なる接頭辞を使うのが安全。
- テンプレートの「計画の承認待ち」は、自律実行では省略した。
