# 第 6 章 機能追加（Spec 駆動の変更）

**ゴール**: 既存アプリに機能を安全に追加する反復手順を身につける。この章の成果（Spec）は、第 7 章の並列開発の入力になる。

## 6.1 講義: 機能追加の標準フロー

```text
1 Issue 作成 → 2 Spec 追記/新規 → 3 影響調査(読み取りのみ) → 4 Plan → 5 テスト先行
→ 6 実装 → 7 openapi/ドキュメント更新 → 8 CI → 9 レビュー → 10 マージ → 11 デプロイ
```

**影響調査プロンプト（既存コードの理解は Agent の得意分野）**

```text
S-005 を実装する前に、既存コードの影響範囲を調査して(変更はしない)。
変更が必要なファイル、破壊的変更になりうる API/DB スキーマ、既存テストへの影響、
後方互換性の維持方法を報告して。
```

## 6.2 追加する機能の候補（3 つ選んで第 7 章でも使う）

## 6.3 ハンズオン A: S-005「担当者・期限・ラベル」（60 分）

`docs/spec/S-005-assignee-due-labels.md`（抜粋）

```markdown
## 受け入れ基準
- Task に assignee(任意,文字列100字), dueDate(任意,ISO8601日付), labels(0〜5個,各20字) を追加
- 既存クライアントは影響を受けない（追加項目は任意で後方互換）
- GET /tasks?assignee=&label=&dueBefore= で絞り込み
- 期限超過(dueDate < 今日 かつ status!=done)の Task は UI で強調表示
- 既存データはマイグレーション後もそのまま読める
```

進め方:

1. 影響調査プロンプトを実行 → 結果を Spec の「未決事項」に反映
2. Plan 確認（マイグレーションが **追加のみ（expand）** で後方互換か点検）
3. テスト先行 → API → UI の順に、それぞれ別依頼・別コミット
4. `openapi.yaml` 更新と `gen:api` 再実行
5. CI → PR → レビュー → dev へ自動デプロイ → 画面確認

## 6.4 ハンズオン B: 不具合修正も Spec 駆動で（30 分）

不具合報告は再現手順をそのまま渡し、**失敗するテストを先に書かせる**。

```text
バグ: PATCH /tasks/{id} で labels を空配列にしても更新されない。
1) 再現する失敗テストを追加 2) テストが失敗することを確認 3) 最小修正 4) 全テスト実行
関連しないコードは変更しないこと。
```

## 6.5 ハンズオン C: リグレッション防止（30 分）

- 既存の契約テスト/E2E が全て通ることを毎回確認
- API の互換性チェック（openapi の差分検知ツールを CI に追加）

```text
CI に openapi.yaml の破壊的変更検知を追加して。main との差分で互換性を壊す変更があれば失敗させる。
```

## 6.6 DB 変更の安全な進め方（expand / contract）

1. **Expand**: 追加のみのマイグレーション（NULL 許容列）→ デプロイ
2. **Migrate**: アプリを新列対応にし、データ移行
3. **Contract**: 旧列削除は別リリースで

Agent には「破壊的 DDL（DROP/型変更）は禁止。必要なら提案のみ」と指示し、AGENTS.md にも記載する。

## 動作確認で判明した注意点(実機検証済み)

- 既存データがある DB への機能追加は、新しいタイムスタンプ付きマイグレーションで列を追加し、既存行は既定値(例: `labels: []`)で埋める。クラウド上の既存データが v2 でも読めることを確認した。
- API 仕様(`docs/openapi.yaml`)を変更したら Web 側で `npm run gen:api` を実行し、型を再生成する。
