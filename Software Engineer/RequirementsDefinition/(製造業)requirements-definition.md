## 1. 目的と要求の扱い

### 1.1 目的

顧客別の受注・納期・台数を起点に、製品構成、部品の手配、設計・組立・試験タスク、担当者間のコメントを同じ生産案件へ統合する。3D／2Dの部品選択と根拠付きAIチャットにより、「何が不足し、誰が何を行い、どの納品に影響するか」を確認できることを目指す。

Phase 1の成功は、第12章の受入試験によって判断する。「生産性が何％向上する」など、実測していない効果は要求根拠・達成実績として扱わない。

### 1.2 記述規則

- **原要求（D）**：ドラフトに明示された事項。
- **補足（P）**：曖昧さの解消、業務整合性、検証可能性のための本件向け提案。メーカーの実際の業務規則を意味しない。
- **要合意（TBR）**：原要求との調整、実環境調査、費用・利用許諾の確認が必要な事項。第13章で担当と期限を管理する。
- **Must**：本書の承認後、Phase 1の必須受入対象。**Should**：優先的に検討する追加機能。**Later**：次期以降。
- 外部資料に基づく説明には `[Sxx]` を付ける。資料の一般論から本件への適用・数値目標を決めた箇所は「本件の提案」であり、資料がその値を推奨しているとはみなさない。
- 要求に一意のID、受入試験にAC番号を付け、原要求との対応を第14章に示す。明確性・実現可能性・追跡性・検証可能性を重視するNASAのチェックリストを採用する。[S01][S02]
- TBRの解消や、原実装の設計段階で確定した要求の明確化には、由来として「（D-15）」「（P-04）」のように判断番号を付ける。番号の要約は付録Bにある。規範となる内容はすべて本文に書いてあり、番号の参照先を読まなくても要求は一意に決まる。
- 要求IDは再利用・付け替えをしない。追加は末尾の番号で行い（例：BR-10、TECH-05）、廃止する場合も欠番として残す。本書の変更は版を上げ、付録Aに記録する。
- 「拒否する」は、確定済みの業務データを一切変えず、利用者に理由を示して操作を終えることを指す。部分的な保存は行わない。
- 「表示する」は、利用者が追加操作なしに画面上で読めることを指す。色だけでの表現は「表示」とみなさない（UI-07）。

### 1.3 別リポジトリで実装するときの前提

- 本書の要求を新しいコードで満たす。原実装のコード・設計・API形状を引き継ぐ義務はない。
- 原実装が作成した独自の3D／2D資産とシードデータは、同じ発注者の成果物であり、再利用してよい。再利用する場合も、本書の要求（UI-01～UI-08、DATA-01～DATA-06）を満たすことを新しい実装で受入試験する。
- 配置先のAzure環境、予算、稼働期間は原実装の環境と同じとは限らない。原実装の環境に固有の確定値（第13章の「原実装での状態」）は引き継がず、TBR-09で改めて決める。

### 3.2 BOM・数量

**BR-01（P・Must）版の固定**：BOM版は「下書き→レビュー中→リリース済み→廃止」とする。レビュー差戻しは下書きへ戻す。リリース済み版の構成・数量は直接編集せず、新版を作る。有効期間・変更理由・記録者・日時を保持する。既存案件への新版適用は自動で行わない。未完了かつ未取消の案件が参照しているBOM版は廃止できない（P-01）。[S03]

**BR-02（P・Must）構成の検証**：親子の循環、複数の根・どの親にも属さない構成位置、同じBOM版内での構成位置ID重複、存在しない部品版、数量0以下、単位不一致を拒否する。親アセンブリーは「子へ展開するグループ」または「購入単位」のどちらかとし、購入単位は子を所要量計算に重複加算しない。ソフトウェア・図面など在庫を持たない品目は「参照」の構成位置とし、所要量・引当・発注の対象にしない。

**BR-03（P・Must）所要量の計算**：各末端の在庫管理品目について、1台当たり所要量は根から当該構成位置までの数量の積とする。同一品目版が複数位置にあれば位置ごとに計算して合算する。案件総所要量は1台分の所要量×製造台数とする。参照品目（REF）・図面は関連対象だが物理在庫・購入不足数には算入しない。

以下の数量は同じ品目版・単位、同じ案件、同じ取得時点で算出する。安全在庫はPhase 1では0とする。

- 使用可能在庫：受入検査合格済みの現物在庫。検査待ち、不合格、返品済みを除く。
- 未引当使用可能数＝使用可能在庫－全案件への有効引当数。
- 未充足所要量＝案件総所要量－当該案件の消費済み数－当該案件の有効引当数。
- 新規手配必要数＝max（0, 未充足所要量－当該案件向けの有効発注未入荷数－当該案件向けの受入検査待ち数）。
- 現物不足数＝max（0, 未充足所要量）。未入荷や検査待ちはこれを減らさない。

未引当在庫は、ユーザーが引当を確定するまでは特定案件の供給として計上しない。新規手配必要数が0でも、検査待ち・入荷遅延により組立不可である場合がある。不合格となった受入数量は検査待ち供給から除外し、必要な追加手配を再計算する。発注未入荷数と検査待ち数の和が未充足所要量を超える場合は、新規手配必要数を0とし、余剰として見直しを促す表示を出す。品目の版または単位が異なる数量は合算しない。

**BR-04（P・Must）不変条件**：全案件の引当合計は使用可能在庫を超えない。案件ごと・品目版ごとに「消費済み数＋有効引当数」は案件総所要量を超えない。消費は当該案件の引当を減らすと同時に現物在庫を減らす。二重クリック・通信再送で入出庫・発注・納品を二重計上しない。品目間・案件間をまたぐ引当確定は全件成功または全件取消とする。不変条件を破るデータを検出した場合は、負値を0に丸めて正常と表示せず、整合性異常として示す。

組立開始時には、案件引当のうち個体へ未割付の分から当該個体の1台分を固定割付する。割付は引当の内訳の移動であり、引当の追加ではない。同じ引当を複数個体の開始条件に再利用しない。割り付けるロットと、台数減で取り消す個体は利用者が明示的に選ぶ（D-15、P-03）。案件全体の消費数が足りていても、個体ごとの充足を確認してから試験開始を許可する。

**BR-05（P・Must）受入**：発注明細ごとに数量・希望日・回答納期・受入数量・合格／不合格数を記録する。部分入荷を許容し、未受入残数を維持する。未入荷残＝発注数量－受入累計－未入荷残の取消累計とし、0未満になる受入（過入荷）を拒否する。未入荷残の取消は入荷完了と区別し、取消数量を別に表示する。不合格分や取消分の再手配は元の明細へのリンクを持つ新たな発注明細で記録し、元の不合格・取消の記録は残す（P-02）。受入日・判定日に未来日を登録しない。

**BR-06（P・Must）変更と取消**：案件内のどの個体も組立を開始していない間に限り、案件BOM版・受注数量を変更できる。変更前後・理由を残し、所要量再計算と過剰引当解放を同一確定操作で実施する。既存の発注残は自動取消せず「見直し必要」と表示する。いずれかの個体が組立を開始した後のBOM版／数量変更、部分製造後の受注取消はPhase 1では拒否し、次期課題とする。数量を0にする変更は受け付けず、全取消の操作へ案内する。組立前の全取消では引当を解放し、未完タスクと発注残の処置（取消、または別の有効案件への付け替え）を確認してから、有効な全個体の取消と同時に確定する。処置できない発注・受入が残る場合は取消を拒否する。

数量変更時は未着手の製造個体を追加または取消として記録し、有効な個体数を変更後台数と一致させる。取り消す個体は利用者が明示的に選ぶ。個体IDは再利用しない。納期だけの変更は組立開始後も理由付きで許容し、元の約束日を履歴に残す。BOM変更で無効になった完了条件は再確認タスクとして扱い、設計ゲートを再判定する。

**BR-10（P・Must）受入品質の訂正**：合格済みで未消費の部品を不合格または検査待ちへ訂正する場合は、対象ロット・数量・元の結果・理由と、影響する引当・個体割付を示す。品質区分の変更、影響する引当と割付の解放、数量の再計算、影響する案件の保留を一体で確定する。組立開始済みの個体の割付を解放した場合も、過去の開始記録は消さず、充足不足を後続ゲートの阻害として残す。Phase 1では、再合格や在庫補充だけで割付・保留を自動復元しない（D-16、P-08）。消費済み数量の合否訂正は拒否し、元記録を保持したうえで影響確認と案件保留を案内する。不合格から合格への訂正も、理由と根拠を付けた追加記録とする。

### 3.3 状態を混同しない

| 対象 | 状態／表示規則 |
| --- | --- |
| BOM版 | 下書き→レビュー中→リリース済み→廃止。レビュー中→下書き（差戻し）。それ以外の遷移（リリース済み→下書き、廃止→リリース済み等）は拒否 |
| 品目の手配表示 | 案件・品目版ごとに数量と明細から導出し、入力はさせない。次の順で最初に当てはまる値とする（P-07）：①案件BOM版が未リリースなら**未計画**（所要量は試算として表示）、②新規手配必要数＞0なら**手配必要**、③発注未入荷＞0で、その需要への受入実績があれば**部分受入**、なければ**発注中**、④それ以外は**受入完了**（検査待ちを含む場合は「検査待ち・使用不可」を併記）。どの値でも現物不足数を併記する。ソフトウェア等の非在庫品目は「非該当」 |
| 購買発注明細 | 下書き→発注済み→部分入荷→入荷完了。下書きは履歴付きで取消できる（下書き取消）。発注済み・部分入荷の明細は未入荷残だけを取り消せる。発注数量をすべて受け入れた明細は「入荷完了」、未入荷残を取り消して未入荷残が0になった明細は「受入終了（残取消あり）」と表示し、入荷完了とは区別する。入荷完了・受入終了・下書き取消は終端で、それ以上の受入・取消を拒否する |
| 受入品質 | 検査待ち→合格／不合格。数量を分けて判定できる。訂正は理由付きの訂正記録（BR-10） |
| タスク | 未着手→進行中→レビュー待ち→完了。レビュー待ち→進行中の差戻しを許容。未着手／進行中／レビュー待ちから保留・取消へ移れる。保留・取消からの復帰は元の状態へ戻し、後続への影響を検査する。完了からの直接の保留・取消は不可。完了の取消（進行中へ戻す）は後続に影響しない場合だけ許可する（D-14） |
| タスク期限超過 | 状態ではなく属性。完了・取消以外（保留を含む）で、期限日の翌日00:00 JSTを過ぎれば期限超過。期限未設定は「未設定」と表示し、超過なしとはみなさない |
| コメント | 未解決⇄解決。編集は改訂として履歴に残す。無効化した場合は現在の内容として扱わず、AIの根拠にもしない。解決・無効化はタスクや合否を変えない |
| 製造個体 | 未着手→組立中→試験待ち→試験中→合格→納品済み。試験中→手直し（不合格）→試験中（再試験）。未着手→取消（組立前の数量減・全取消のみ）。合格→手直し、納品済み→合格、組立中→未着手、取消→未着手の遷移は提供しない |
| 生産案件 | 第3.4節の工程＋保留フラグ＋各工程の台数内訳。終端は「完了」と「取消」の2つで、相互に変換しない。単一状態で全台同時進捗と誤認させない |

親部品に複数の問題がある場合、代表表示は「不合格／保留→現物不足→作業中→完了→未着手」の順とする。不合格と保留が同時にあれば両方を表示する。「完了」は関連する作業・供給条件がすべて完了した場合だけとし、関連タスクが0件であることだけを理由にしない。調達・品質・タスクの各件数／数量を必ず併記し、代表色だけで判断させない。読み取れなかった値を0件や完了として表示しない。この優先順は本件の表示提案である。

### 3.4 生産ワークフローとゲート

受注→設計→調達・部材準備→組立→試験→納品とする。調達は設計と並行して記録可能だが、未リリースBOMからの正式引当・発注確定は拒否する。標準品の「設計」は毎回の新規設計ではなく、使用版の選定・仕様確認も含む。[S03][S04]

必須タスクは、案件必須（案件の全個体に適用）または個体必須（指定した1個体に適用）とし、どのゲートの条件か（設計・組立・試験・納品のいずれか）を「対象工程」として必ず持つ。担当領域から対象工程を推測しない。参考タスクはゲートを阻害しない。下表の「必須〇〇タスク」は、対象工程が〇〇の必須タスクを指す。

| 移行 | 必須条件 |
| --- | --- |
| 受注→設計（設計開始） | 顧客、機種、本体型式、仕様、正の台数、納期、生産担当を登録済み |
| 設計→調達・部材準備（設計ゲート） | 使用BOM版リリース済み、必須設計タスク完了、案件に固定したモデル版が公開済み（UI-08） |
| 個体の組立開始 | 設計ゲートが現在も有効、当該1台分の全在庫管理品目を当該個体へ割付できる（BR-04）、案件保留なし |
| 個体の組立完了（組立中→試験待ち） | 記録者・日時を記録する。この時点で消費の記録漏れや必須組立タスクの未完があっても記録はできるが、試験開始の阻害として表示する |
| 個体の試験開始 | 組立完了、当該個体の全所要部材の消費記録済み、必須組立タスク完了、案件保留なし |
| 個体の合格 | 当該個体に適用する試験定義の必須項目がすべて有効な合格（BR-11）。未実施・不合格・手直し中がない。必須試験タスク完了。案件保留なし |
| 個体の納品 | 個体合格、必須納品タスク完了、納品日・受注明細・個体ID登録済み、案件保留なし |
| 案件完了 | 受注明細の全有効個体を納品済み。未解決の必須タスク・残引当・保留がない |

ゲートの通過記録は過去の事実であり、次の操作の許可証ではない。各操作の時点で、BOM版・タスク・割付／消費・試験・保留を改めて検査する。

画面上部は各工程の未着手／進行中／完了と台数を表示する。案件の現在工程は、設計ゲートが未通過または再確認が必要なら「設計」、通過後は未納品の有効個体のうち最も早い工程とする。個体状態と工程の対応は、未着手＝調達・部材準備、組立中＝組立、試験待ち・試験中・手直し＝試験、合格＝納品とする。部分納品時は「一部納品 X/Y台」を併記する。保留と再確認の必要は工程の上に重ねて表示し、工程を書き換えない。工程バッジの直接編集によるゲート迂回は禁止する。

**BR-07（P・Must）差戻し**：試験不合格時は原因・対象個体／部品・手直しタスクを登録し、再試験結果を履歴として追加する。再試験では当該個体の必須試験項目をすべて再実施し、旧い合格記録で新しい不合格を隠さない（P-04）。保留の扱いはBR-12による。BOM・タスクの完了取消、または必須タスクの追加により通過済みゲートが無効になる場合、後続を自動巻戻しせず更新を拒否し、影響確認と案件保留を求める。Phase 1では通過後の例外承認手続を設けない（P-06）。

**BR-08（D/P・Must）分納**：納品数量は合格済みかつ未納品の個体を選んで集計し、受注台数を超えない。同一個体の重複納品は禁止。選んだ個体に1台でも不適格があれば、その納品操作全体を拒否する。納品実績の日付に未来日を登録しない（P-05）。残数＝受注台数－累計納品台数とし、顧客が同じでも異なる納期明細の残数を混ぜない。Phase 1では1明細から複数ロットへの分割を行わず、同じ案件内の個体別進捗と分納で表現する。

**BR-09（P・Must）日付と警告**：約束納期・部材必要日・タスク期限は日本時間の日付として扱い、操作時刻はUTCで保存しJSTで表示する。納期日終了（翌日00:00 JST）までに残数が0にならなければ納期超過。回答入荷日が必要日を過ぎる、または必要日超過で現物不足がある場合は「遅延リスク」を表示する。回答入荷日が未登録の発注を予定どおりとみなさない。これは規則による注意喚起であり、能力計画を考慮した納期保証ではない。

判定に使う「現在日時」は、実時刻、または運用設定で固定した評価日時のどちらかとする。固定している間は、全画面に評価日時を表示し、AI回答の参照時点もその日時にそろえる。受入試験は第8.3節の基準日時に固定して行う。

**BR-11（P・Must）試験定義**：製造個体試験は、版付きの試験定義に基づいて記録する。試験定義は項目ID、必須／参考、入力型（Phase 1は真偽値）、判定方法、由来を持ち、使用した版を試験結果に固定する。Phase 1はメーカーの実試験基準を使わず、架空の定義1版を3機種の個体に共通で使う。必須項目は「デモ版ラベル照合（個体の表示と案件の固定BOM版・モデル版が一致するか）」と「デモ記録添付確認（試行に根拠文書が紐付いているか）」の2つとし、どちらも人が確認して真なら合格、偽なら不合格とする（D-17）。値がない項目は未実施であり、偽（不合格）とは区別する。必須項目が0件の定義、参考項目だけの合格、他の個体や古い版の結果は、個体の合格の根拠にしない。試験定義の編集画面は設けず、シードデータで提供する。

**BR-12（P・Must）案件保留**：保留は、未完了かつ未取消の案件のどの工程でも、理由と記録者を付けて開始できる。保留中に別の原因が見つかった場合は、既存の理由を上書きせずに追記する。保留中は、組立開始・消費・組立完了・試験開始（再試験を含む）・合格・納品・案件完了を拒否する。コメント、懸念の記録、保留の原因を解消するタスクや根拠の記録、納期変更、照会は許可する。入荷と受入検査の事実も記録できる。解除には理由と記録者を必須とし、記録されたすべての原因が解消したことを確認する。解除だけでゲート通過・合格・引当を復元しない。BR-10の品質訂正で生じた保留は、Phase 1では解除しない。

### 4.1 AIによる生産状況分析（FR-28、AI-13）

出典：2026-10-02の依頼原文「案件の詳細ページの画面の一番上に、生成AIで作成した現状の生産状況の分析の説明を掲載する」。

1. **表示位置と内容**：個別生産画面の最上部（工程帯などの上部パネルより上）に「AI生産状況分析」パネルを置く。内容は「事実」（各項目に1件以上の根拠リンク）、「注意点（推測）」、「確認できないこと」の3区分とし、「AI生成の参考情報。数量・合否・納期は通常の画面で確認してください」の注記、生成日時（JST `YYYY-MM-DD HH:mm`）、データの参照時点、モデル名を表示する。本文はテキストとして表示し、HTMLとして解釈しない（AI-07）。
2. **分析用データ**：サーバーが正本DBから次を読み取り、根拠ID（ref）付きのJSONにまとめてモデルへ渡す。モデルに読取関数・更新関数は渡さない（AI-06）。①案件（ref `project:<案件ID>`）：顧客、型式、約束納期、受注台数、納品済み、残台数、現在工程、工程帯の各工程の状態と台数、納期超過・遅延リスクの有無、設計ゲートの通過・再確認・阻害理由、案件完了の阻害、整合性異常の件数、保留の有無と未解消の保留理由（利用者入力のため`reason_untrusted`）。②需給（ref `supply:<案件ID>:<部品版ID>`）：現物不足＞0、新規手配必要数＞0、検査待ち＞0、遅延リスクありのいずれかに当たる品目（部品版ID昇順、最大50件）。③製造個体（ref `unit:<個体ID>`）：状態、阻害理由、最新の試験結果（個体ID昇順）。④未完タスク（ref `task:<タスクID>`。状態が完了・取消以外）：件名（`title_untrusted`）、状態、主担当ID、期限、期限超過、対象工程、必須区分（API-07のタスク順で最大50件）。部品コメント本文・設計メモ本文は渡さない。
3. **鮮度の判定**：分析用データから参照時点を除いたものを、キーを辞書順に並べたUTF-8のJSONにしてSHA-256を取った値を「データ指紋」とする。最新の完了済み分析のデータ指紋が現在のデータ指紋と一致すれば「最新」、異なれば「古い」とする。
4. **API**：`GET /api/projects/{id}/analysis` は `available`（AIが構成済みか）、`fingerprint`（現在のデータ指紋）、`state`、`analysis`（最新の完了済み分析。なければnull）、`attempt`（最新の生成試行。状態を問わない。なければnull）を返す。`state` は次の順で最初に当てはまる値とする：①最新の試行が生成中なら`running`、②`analysis`のデータ指紋が現在と一致すれば`fresh`、③最新の試行が失敗でそのデータ指紋が現在と一致すれば`failed`、④`analysis`があれば`stale`、⑤それ以外は`none`。`POST /api/projects/{id}/analysis` は生成を要求する（`X-CMS-Request: 1`と同一オリジンが必須：API-04。業務データを変えないためIdempotency-Keyは不要）。次の順に判定する：(a) 案件がなければ404 `NOT_FOUND`、(b) AI未構成なら503 `AI_UNAVAILABLE`、(c) 生成中の試行があればそれを202で返し新たに呼び出さない、(d) `fresh`ならその分析を200・`reused: true`で返しモデルを呼び出さない、(e) AIの同時実行（チャットと合算）が上限ならば429 `AI_BUSY`、(f) AI-12の予約（1質問として数える）が上限を超えるなら422 `AI_LIMIT_REACHED`（試行を記録しない）、(g) それ以外は試行を「生成中」で記録して202を返し、非同期で生成する。
5. **生成**：モデル呼出しは1回の生成につきAI-12の「1質問あたりの呼出し上限」（一時障害の再試行を含む。A-15）以内、一時障害の再試行は最大2回、60秒で打ち切る（AI-09）。回答はJSON（`facts[{text, refs}]`、`inferences[{text}]`、`unknowns[{text}]`）とし、`refs`に分析用データにないrefが1件でもあれば分析全体を失敗（`citation_invalid`）とする。refのない事実は「確認できないこと」へ移す（A-05と同じ規則）。失敗の種別は`timeout`・`rate_limited`・`quota`・`server`・`invalid_answer`・`citation_invalid`・`call_limit`・`internal`のいずれかとする。費用は呼出し後に実績で精算する（AI-12）。
6. **画面の動作**：画面表示時にGETし、`available`が真で`state`が`none`または`stale`のときだけ、その表示につき1回だけ自動でPOSTする。生成中は「生成中」を表示し、2秒間隔で最大70秒GETする。`stale`の間は前回の分析を「データ更新前の分析」と明示して表示する。`failed`は失敗理由と「再生成」ボタンを表示し、自動では再要求しない。`available`が偽、またはPOSTが拒否された場合は「AI分析は利用できません」と理由を表示し、画面の他の機能は通常どおり使える（FR-23）。
7. **記録**：試行ごとに、試行ID、案件ID、データ指紋、状態、失敗種別、モデル名、呼出し回数、入出力トークン数、予約額・実績額、処理時間、参照時点、要求者のデモユーザーID、作成・完了日時を保存する（AI-08）。分析は業務事実の正本ではなく、AIの文書索引（AI-03）にも入れない。

### 4.2 ガントチャート（FR-29）

出典：2026-10-02の依頼原文「案件とタスクのページでは、ガントチャートでプロジェクトとしての進捗状況表示するようにしてください」。日付はすべてJSTの暦日（BR-09）とし、操作時刻はJSTの日付に変換して使う。「評価日」は評価日時（BR-09）のJSTの日付とする。

1. **案件の進捗率**：完了した案件は100。それ以外は ⌊100 ×（D＋ΣU）÷（1＋5N）⌋。Dは設計ゲートが通過済みで再確認が不要なら1、そうでなければ0。Nは取消以外の製造個体の数。Uは個体ごとに、未着手0、組立中1、試験待ち2、試験中3、手直し3、合格4、納品済み5。例：4台中2台が納品済み・2台が試験待ちで設計ゲート通過済みなら ⌊100×(1+5+5+2+2)÷21⌋＝71。
2. **案件のバー**：開始＝受注日（受注を登録した操作日時のJSTの日付。評価日時を固定していても操作日時を使う）、終了＝約束納期（受注日が約束納期より後なら開始＝約束納期）。案件ID、顧客、型式、進捗率（％）、現在工程、納品済み／受注台数、納期超過を文字で併記する。
3. **工程のバー（個別生産画面だけ）**：工程帯（第3.4節）の6工程それぞれについて、状態は工程帯と同じ値（未着手／進行中／完了）とする。開始・終了は次による。受注：開始＝受注日、終了＝設計開始日。設計：開始＝設計開始日、終了＝設計ゲート通過日。調達・部材準備：開始＝設計ゲート通過日（未通過なら受注日。調達は設計と並行して記録できるため：第3.4節）、終了＝取消以外の全個体の組立開始日の最大。組立：開始＝組立開始日の最小、終了＝組立完了日の最大。試験：開始＝組立完了日の最小、終了＝合格日の最大。納品：開始＝合格日の最小、終了＝納品記録の納品日の最大。状態が未着手の工程はバーを持たない（開始・終了ともnull）。進行中の工程の終了は評価日とする（開始が評価日より後なら開始日）。開始を上の規則で決められない進行中・完了の工程は開始＝評価日とし、終了が開始より前なら終了＝開始とする。
4. **マイルストーン**：約束納期、元の約束納期（変更された場合だけ）、部材必要日（登録されている場合だけ）、評価日。
5. **タスクのバー**：開始＝タスクの作成日、終了＝期限。期限が作成日より前なら開始＝期限。期限未設定のタスクはバーを持たず「期限未設定」と表示する。件名、状態、主担当、期限超過を文字で併記する。並び順はAPI-07のタスク一覧の順。
6. **API**：`GET /api/projects/{id}/gantt` は `evaluated_on`、`project`（第2項）、`stages`（第3項。工程の順）、`milestones`（第4項）、`tasks`（当該案件の全タスク）、`range`（応答に含まれるすべての日付の最小と最大）を返す。`GET /api/gantt` はタスク一覧（FR-09）と同じ抽出条件と`include_cancelled`を受け付け、`evaluated_on`、`range`、`projects`（案件ID昇順。各案件に第2項の値と、抽出条件に一致したタスク`tasks`）を返す。取消済み案件は`include_cancelled=true`のときだけ含める。案件以外の抽出条件が1つでもあれば、一致するタスクが1件以上ある案件だけを含める。抽出条件の値が不正なら400 `VALIDATION_ERROR`。
7. **画面**：個別生産画面では上部パネルの直後に案件のガントチャート（案件・工程・タスク）を、共通タスク画面ではタスク一覧の前に案件横断のガントチャート（案件ごとに案件のバーとその案件のタスク）を表示する。横軸は日単位で月の境界に目盛と`YYYY-MM`の文字を付け、評価日に縦線を引く。バーの状態は色だけでなく文字（「完了」「進行中」「未着手」「期限超過」、進捗率）で示す（UI-07）。タスクの行は件名からタスク詳細へ移動できる。日程はガントチャート上で編集しない。

### 4.3 画面部品の開閉（FR-30）

出典：2026-10-02の依頼原文「案件の詳細ページの特定の画面コンポーネント縦に長すぎます。それぞれの画面コンポーネントを表示したり閉じたりできるようにしてください」。

1. **対象**：個別生産画面の次のパネル。AI生産状況分析、個別生産（上部）、ガントチャート、製造個体、BOMツリー／部品一覧、ビューア、詳細、AIチャット、および詳細の中の各小見出しの区画（案件全体の需給、引当、案件コメント、保留履歴、案件完了阻害、全体タスク、未対応コメント、発注明細、納期履歴、部品選択時の各区画）。
2. **操作**：各パネルの見出し行に開閉ボタンを置く。ボタンの文字は開いているとき「閉じる」、閉じているとき「表示」とし、`aria-expanded`と`aria-controls`で状態を示し、キーボード（Enter／Space）で操作できる。閉じたパネルは見出し行だけを表示し、本文を表示しない（本文は画面上に残したまま非表示にする）。本文の入力内容・部品の選択・チャットの会話は閉じても失われない。画面上部に「すべて表示」「すべて閉じる」を置く。
3. **既定と保存**：既定はすべて表示。開閉状態はブラウザーの`localStorage`のキー`cms.panel.<パネルID>`に`open`／`closed`で保存し、再読込・他の案件への移動後も同じパネルIDに適用する（案件ごとには分けない）。`localStorage`を使えない場合は既定で表示し、開閉は画面表示中だけ有効とする。開閉状態は他の利用者に同期しない。

### 4.4 製品モデル画面の3D／2Dと部品の公開情報（FR-31、FR-32）

出典：2026-10-02の依頼原文「製品モデルのサイトに、製品の3D/2D表示を表示させてください」「3Dのコンポーネントを、実際の顧客の製品のリアルな各部品の情報が取得できるようであれば、入手して、それを表示してください」。

### 4.5 部品コメントのモデル上表示（FR-33）

出典：2026-10-02の依頼原文「案件の詳細ページで、3D\2Dに関わらず、製品BOMのコメントがあれば、2D/3Dモデル上にポップアップとしてわかるようにして、それをクリックしたらコメントを作成・編集できるようにしてください」。

1. **マーカーの対象**：当該案件の構成位置ごとに、無効化していないコメント（返信を含む）を数える。1件以上ある構成位置にマーカーを表示する。マーカーの文字は「💬 未解決n／全m」（nは未解決、mは無効化以外の件数）とし、未解決が1件以上なら「!」を前に付ける（色だけで区別しない。UI-07）。
2. **位置**：3Dでは、構成位置に対応するメッシュの外接直方体の上面中心（説明マーカーの位置にある内部部品はその位置）に、画面上の重ね表示として置き、カメラ操作に追従させる。2Dでは、表示中の方向の図で同じ構成位置の図形の外接矩形の右上に置く。モデル上に図形がない構成位置（一覧選択のみ、または現在のモデル版に対応がない）は、ビューアの「位置のない部品のコメント（k件）」ボタンから一覧で開く。マーカーは他の利用者に同期しない（UI-05）。
3. **クリック時の動作**：マーカーをクリック（またはEnter／Space）すると、その構成位置を選択し（FR-18の詳細も更新）、コメントのポップアップ（モーダルのダイアログ）を開く。ポップアップには、構成位置ID・部品名と、その構成位置の無効化していないコメントを作成日時の昇順で、ID・状態・本文・投稿者・日時・版とともに一覧する。操作：新規コメント（本文、任意の対象個体）、返信、本文の編集（改訂履歴が残る：FR-12）、解決／再開。保存は既存のコメントAPI（FR-12、API-03～API-06）を使い、版競合（409）では入力を保持して最新の再読込を案内する（FR-20）。保存に成功したらポップアップの一覧、マーカー、部品詳細を更新する。部品を選択しているときは、マーカーがなくても「選択部品にコメント」ボタンから同じポップアップを開ける。
4. **対象外**：コメントの局所座標（UI-03）の画面上での指定・表示、コメントの削除（Phase 1で無効化だけを提供：FR-12）。

## 5. ダミーログインとWindows氏名の扱い

### 5.1 原要求と実現制約

原要求は「認証処理なし」「Windowsにログイン中のアカウントで入場」「Full Nameを表示」の3点である。しかし、**通常のWebサイトのHTML／JavaScriptが、追加連携・認証なしにWindowsログオン利用者のFull Nameを自動取得する前提は置けない**。Azure側のPythonが取得するOSユーザーはサーバープロセスの実行者であり、利用者のWindowsアカウントではない。

Microsoft EdgeのWeb SSOは対応するサイト・ID基盤を必要とし、Windows統合認証も認証要求とイントラネット／許可先の条件を持つ。ブラウザにサインイン済みであることと、任意のWebアプリが氏名を取得できることは別である。[S11]

### 5.2 選択案（TBR-01）

| 案 | 内容 | 原要求との差／扱い |
| --- | --- | --- |
| A：Phase 1推奨 | 初回のみ架空デモ利用者を選択、または表示氏名を入力。次回はそのブラウザに保存された選択で入場 | 認証不要だがWindows自動取得を満たさない。発注者の代替承認が必要 |
| B：追加開発 | 利用者PC上の承認されたローカル補助プログラムがWindows表示名を取得し、確認後にアプリへ渡す | Web単体ではない。導入・アカウント種別別の取得可否・通信経路の検証が必要。本人認証にはならない |
| C：次期推奨 | Microsoft Entra ID／App Service認証とSSOを使い、アプリに渡された表示名を使用 | 利用者の再入力を減らせるが「認証なし」とは異なる。WindowsローカルFull Nameと常に一致する保証もない |

本書の他機能はA案を前提とするが、**A案を実装して原要求のWindows自動取得まで達成したと報告しない**。自動取得が必須ならB／Cの方式と費用を決めてからFR-01を改訂する。氏名未設定・取得失敗時は推測せず表示名確認画面へ戻す。パスワード・OS認証情報は取得しない。

**確定状況**：Phase 1はA案を採用した（D-03）。表示氏名の自由入力は行わず、登録済みのデモ利用者から選ぶ。ブラウザに保存した選択は、次回の起動時にその利用者が存在し有効であることを確かめ、無効なら推測せず入場画面へ戻す。原要求の「Windowsアカウントの Full Name 自動表示」は**Phase 1では満たさない既知の差異**であり、発注者が最終受入で確認する。B案・C案は次期の検討対象とする。

表示名と不変のデモユーザーIDを分離する。同名でも異なるIDとして管理し、表示名変更で過去の投稿帰属を変更しない。実在する氏名を使う場合は本人の同意とデモ公開範囲を確認する。

### 6.2 モデル・図面と部品の対応

- **UI-01（P・Must）**：モデルの描画ノードを、`productModelId + modelRevision + bomRevisionId + occurrenceId` に対応付ける。同一品目の左右や繰返し配置をノード名・画面座標だけで識別しない。
- **UI-02（D/P・Must）**：各対象機種に20以上の選択可能な構成位置を用意する。1位置を複数メッシュで表してよいが、メッシュ数を部品数として数えない。非表示の内部部品とソフトウェアはBOMツリー／説明用マーカーから選択する。
- **UI-03（P・Must）**：コメントは案件ID・構成位置・対象モデル版・任意の局所座標に結び付ける。個体固有の問題には個体IDも付ける。モデル更新時は対応表を検証し、未対応注釈を一覧に残す。別部品へ推測移動しない。
- **UI-04（D/P・Must）**：2Dは各方向の独自線画／正投影の簡略図と選択領域を提供する。3Dのカメラだけを変えて「設計図」と呼ばず、方向・図面ID・版・縮尺保証なし・製造利用不可を明示する。MODEL-Lは旧版・新版のそれぞれに6方向を用意し、全体で4資産セット・24方向図とする（D-12）。正規図面入手後は別版として登録する。
- **UI-05（P・Must）**：利用者間でカメラ位置は自動同期しない。「同じ画面」とは同じ案件・部品構成・モデル版・保存済みデータを共有する意味とする。追従視点はShouldで、共有開始／終了を明示する。
- **UI-06（P・Must）**：3D読込失敗／WebGL非対応でもBOM一覧と2Dから部品・タスク・コメントへ到達できる。2D／3D切替で選択部品・案件を保持する。
- **UI-07（P・Must）**：状態は色だけでなく名称・アイコン・数量で表す。キーボードで検索、BOMツリー、タスク、コメント、チャットを操作できる。3Dの代替に部品一覧を提供し、フォーカスを可視化する。正式なアクセシビリティ規格適合の認証までは本フェーズに含めない。
- **UI-08（P・Must）**：モデル版は、3Dモデル・6方向の2D図面・構成位置との対応表を1組にした、BOM版に対応する版とする。運用者の登録操作で登録し、対応表の検証（UI-01・UI-02：BOM版の全選択可能位置が3Dまたは2D／一覧から選べ、存在しない位置を指していない）に合格したものだけを「公開済み」にする。公開済みのモデル版の内容は変更せず、変更は新しい版として登録する。設計ゲートは、案件に固定したモデル版が公開済みであることを条件にする（第3.4節）。
- **UI-09（P・Must、v1.8で追加）形状定義の回転と寸法の根拠**：形状定義の各メッシュは任意の`rot_z`（度。-180以上180以下の数値。機械前方xから上方yへ向かう向きを正とする、z軸＝機械左方向まわりの回転）を持てる。3Dでは軸合わせの後にメッシュ中心まわりで回転する。2Dでは、直方体は`size`、円柱は軸方向に`length`・他の2方向に直径の8頂点を回転して投影した凸多角形で描く（回転なしで軸が奥行き方向の円柱は円）。各メッシュは`basis`（`public_dimension`＝DATA-07の公開値に基づく寸法を含む、`schematic`＝模式）と`facts`（使った公開事実の項目IDの配列）を持てる。`basis`が`public_dimension`なら`facts`は1件以上、`schematic`または省略なら`facts`は空とする。この規則・`rot_z`の範囲に反するモデル版は対応表の検証に失敗とし、公開できない（UI-08）。3D／2Dの注記は「主要寸法の一部は公開仕様値に基づく／形状は模式／製造利用不可」とし、公開値に基づく部品も形状は模式であることを示す。

モデル形式はWeb配信向けGLB／glTF 2.0、2Dは安全なSVG／PNGを推奨するが、要求は部品対応と表示動作であり、レンダリングライブラリーの選定は詳細設計で行う。DWG・STEP・ネイティブCADのブラウザ直接編集や自動変換は含めない。

## 7. AIチャット／RAG要求

RAGは外部の検索可能な知識を生成に組み合わせる方法であり、引用可能な情報へのアクセスや知識更新に有用である。ただし、RAGを使うだけで回答が正しいことは保証されない。Lewisらの論文はWikipediaを用いたNLP課題の研究であり、本件のBOM・在庫管理精度を証明するものではない。[S05] 本件ではAzureのRAG設計・準備・評価ガイドに従い、質問と正解根拠を先に整備する。[S06][S07][S08]

### 7.1 「全てのデータ」の境界

| AI-12 | P・Must | 有料のAI利用量に、アプリ側で上限を設ける。既定値は、同時実行が全体2件・1セッション1件（SEC-02）、1質問あたりのモデル呼出し3回まで、質問数が1日200問・総数1,000問、生成費が1日2,000円・総額10,000円とする。値は運用設定で変更でき、TECH-03で承認した予算を超えない値にする。上限はアプリ全体（全利用者・全データ世代の合計）で数える。日次の上限はJSTの00:00に戻り、総数・総額は運用者が明示的に戻すまで累計する。入力検証で受け付けなかった質問は数えず、受け付けた質問は再試行を含めて1問と数える。費用は、モデルを呼び出す前に最大見積額を予約し、予約を含めて上限を超えるなら呼び出さない。呼出し後に実績額で精算する。上限に達したら新しい質問を受け付けず、理由と再開の目安を表示する。上限の判定に必要な記録を保存できない場合は、有料の呼出しを行わない |
| AI-13 | P・Must（v1.8） | AIによる生産状況分析（FR-28）にも、AI-04～AI-10・AI-12を適用する。分析は1回の生成を1質問として数え、チャットと同じ上限・同時実行数（SEC-02）を共有する。データ指紋が変わらない限り再生成しない（第4.1節）。分析にはツール（読取関数・更新関数）を渡さず、利用者が入力した文字列は`_untrusted`の項目として渡し、その中の命令に従わない（AI-07） |

| ASM-3 | 同上（KEYを含めてよい） | 在庫照会、KEYの発注、受入検査、試験記録 |
| ASM-4 | 同上（PAIRの左右2位置を含めてよい） | 組立タスク、左右部品のコメント確認 |
| ASM-5 | 同上（REFへの参照位置を含める） | 設計レビュー、試験、REF適用版の確認 |

各ASMに、第0.2節で決めた末端品目を割り当てる。5つのASMの末端品目は合計で、購入単位（在庫・発注の対象）24（PAIRは同じ品目の2位置）とし、全技術領域（DOM-1～DOM-5）のタスク例が各ASMの品目に結び付くようにする。

品目略称には実データで`DEMO-L-`を付ける。対称部品（PAIR）は同じ品目の2構成位置である。公開仕様の個数は参考にするが、組番号・内部部品数は架空とする。参照品目（REF）`DEMO-REF`はコントローラーの下の「参照」位置とし（BR-02）、在庫引当の対象にはしない。

**3機種の構成位置**：3機種とも、根（完成品）1、ASM-1～ASM-5の説明用アセンブリー5、末端の購入単位24（上表の品目。対称部品（PAIR）は2位置）、ソフトウェアの参照1の計31位置を基本とし、すべての数量は親1に対して1とする。品目番号の機種部分は`DEMO-L-`／`DEMO-M-`／`DEMO-S-`とし、機種ごとに別の品目とする。構成位置IDは`O-<機種記号>-<略称>`（例：`O-L-KEY`、`O-L-PAIR-L`）とする。機種差は公開仕様に基づき、出典を由来台帳に記録して反映する（DATA-02）。

| 機種 | 基本構成からの差 | 2D／3Dで見分けられるようにする特徴 |
| --- | --- | --- |
| MODEL-L | 旧版（リリース済み）と新版（レビュー中）の2版。新版はKEYの品目版をB版へ変え、ASM-5の1品目を別の構成位置へ置き換える（架空の設計変更） | 基準形状。新版で置き換えた位置 |
| MODEL-M | 公開仕様に基づく中位機種の構成差（該当する品目・位置の追加／置換）。差がなければ寸法だけの差とする | 公開仕様から決めた特徴 |
| MODEL-S | 公開仕様に基づく下位機種の構成差。標準装備として記載がある構成要素は位置を追加する（位置数は機種ごとに記録）。同ページの一部の数値が別仕様での値の場合は区別して記録する [S15] | 公開仕様から決めた特徴 |

形状は模式であり、寸法の一致は求めない。上表の特徴が、3Dと該当する2D方向の図の両方で目視で区別できればよい。

数量シナリオ例：DEMO-001の代表部品（KEY）は10台×1組＝10組必要。合格在庫8組のうちDEMO-002へ3組引当済み、DEMO-001へ5組引当する。DEMO-001向け発注3組、検査待ち0組、消費0組なら、現物不足5組、新規手配必要2組となる。発注3組中2組が入荷し検査合格・引当された後は、DEMO-001引当7組、発注未入荷1組、現物不足3組、新規手配必要2組となる。これは独立した受入試験用スナップショットとする。なお、合格後・引当前の中間状態では、合格品が検査待ちから外れ、未引当在庫は案件の供給に計上しないため、新規手配必要数は一時的に4組となる。これはBR-03どおりの値であり誤りではない。

この試験用スナップショットは`FIXTURE-KEY`としてシードデータとは別に用意し、AC-05とAI評価Q04～Q06の各実行前に復元する。両案件のBOMはリリース済みとし、記載のない同品目の在庫・引当・発注・検査待ちは0とする。試験中の入荷後状態を通常シードへ混入させない。

### 8.5 知的財産と資産提供

**DATA-05（P・Must）**：公式の画像・CAD・ロゴが公開されていることを、自由な再配布・改変の許諾と扱わない。サイト利用条件を確認し、必要な許可が得られるまではリンクと必要最小限の事実参照にとどめる。[S17]

**データの流れ**：ブラウザ→Python API→SQL正本。チャットはPythonの読取処理→SQL最新値＋Cosmos文書検索→モデル呼出し→引用検証→回答。資産はPython経由または有効期限付きの限定URLで配信する。ブラウザからDB／LLMを直接呼ばない。

**SQLを業務正本にする理由**：Cosmos DBはタスク、顧客／注文、AI文脈にも有力で、弾力的スケール、グローバル分散、マルチリージョン書込み、低遅延SLAを活用できる。ただし、それらを使う配置／契約条件と本アプリのE2E性能保証は別である。通常のTransactional Batchは同一コンテナー・同一論理パーティション内が原子性の境界である。[S20] 本件の複数案件に共通する在庫引当を単純な案件別パーティションへ分散すると、原子性の追加設計が必要になる。その複雑性を避けるためSQLを推奨し、CosmosはAI用途の第一候補とする。Phase 1で多地域書込みを有効化する必要はない。

**二重正本を作らない**：SQLとCosmos間の分散トランザクションは前提にしない。文書変更と索引待ち記録をSQLに原子的に保存し、永続キュー相当の記録から再索引する。失敗時は再実行可能にし、CosmosのコピーでSQL数量を上書きしない。初期版はPythonの再開可能な索引処理と運用実行で足りるか検証し、60秒の反映目標を満たすために常駐処理が必要なら、Always On等の条件を確認する。

**追加サービスの判断**：Azure Functionsは再索引・タイマー処理を分離する必要がある場合のみ追加する。Azure AI Searchは文書数・日本語検索品質・ハイブリッド検索の評価でCosmosが要件を満たさない場合の代替とし、最初から2つの検索基盤を運用しない。Key Vaultは秘密を避けられない接続がある場合に追加する。AKS、VM、API Management、Azure Digital TwinsはPhase 1では採用しない。

**小規模ベクトル検索の注意**：公式資料では`flat`は505次元まで、`quantizedFlat`／`diskANN`は1,000ベクトル未満ではフルスキャンになる。[S10] 10案件のデモで大規模ANNの効果を仮定せず、埋込み次元数・件数・RU・品質を実測して選定する。制限を満たすために架空チャンクを水増ししない。HPKも機械的に導入せず、検索対応を確認したうえで、会話は会話ID、知識は高カーディナリティの原本文書ID等をパーティション候補として検証する。1項目へ無制限の会話履歴を埋め込まない。

### 10.1 セキュリティを次期へ送る範囲

原要求の「セキュリティ設定はほぼしない」は、利用者の正式認証・細粒度権限・高度なネットワーク分離を次期とする意図として扱う。**有料AIを上限なしで公開することは、Phase 1の既定にしない**。以下の最小措置は追加提案で、TBR-05にて承認する。[S09][S12][S19]

- **SEC-01（P・Must）**：HTTPSを使用し、DB接続情報・モデルキー・管理トークンをJavaScript、Git、回答、ログへ出さない。サービス間はManaged Identityを優先する。Azureの管理権限は利用者のダミー入場と別管理とする。
- **SEC-02（P・Must、v1.4で変更）**：到達範囲はDEP-04のとおり、すべての接続元IPに公開する（発注者の決定、2026-10-02）。匿名利用者による改変・課金のリスクは、架空データ限定（SEC-05）、運用者操作をHTTPに置かないこと（FR-25）、AI利用量の上限（AI-12）、予算通知（TECH-03）、初期化とバックアップ（FR-25、NFR-07）で抑える。AI同時実行は全体2件、1セッションにつき1件とする。上限超過は待機または明示拒否する。隠されたURLやダミー名を認証の代替とみなさない（公開範囲の全員が業務データを変更できる前提で運用する）。
- **SEC-03（P・Must）**：入力検証、パラメーター化DBアクセス、出力エスケープ、同一オリジンを基本としたCORS／CSRF対策を行う。コメントに含まれるスクリプトを実行しない。
- **SEC-04（P・Must）**：初期資産は運用者が登録した許可形式だけを使用する。SVGのスクリプト／外部参照を除去し、GLBの外部参照を許可しない。一般利用者の任意ファイルアップロードはPhase 1では提供しない。
- **SEC-05（P・Must）**：本人認証・アクセス権限がないため、利用者別の機密性・操作否認防止は保証しない。実顧客・機密BOMを持ち込まない。会話はセッション分離するが、正式な個人情報保護の境界として扱わない。
- **SEC-06（P・Must）**：デモ終了後30日以内にチャット等の不要データを削除し、初期化前には必要な検証成果を退避する。依存関係の脆弱性確認と、費用急増時のAI停止を運用手順に含める。

最小措置を採用しない場合は、閉じたローカルデモ等へ利用形態を限定し、公開Azure運用を別途合意する。本フェーズの合格を本番セキュリティ審査の合格として流用しない。

### 12.1 AI評価セットと合否

20問を固定し、実際のデプロイモデルで各3回、合計60回実行する。本件の受入目標であり、運用全体の正答確率を統計的に保証する試験ではない。[S07][S08]

- 正常系12問：受注／納期3、BOM／在庫／発注3、タスク／コメント3、品質／履歴／公開仕様3。各問に期待値、許容回答、必要根拠IDを人が設定する。
- 例外系8問：未登録情報2、曖昧な範囲1、改版／無効化2、間接プロンプト注入1、サービス障害2。
- 正常系36回答中33回答以上で、質問への回答・必要事項・根拠一致をすべて満たすこと。いずれか欠落した回答はその回を不合格とする。
- 数量・約束納期・合否について、回答した値と正本の不一致は0件。根拠なしの断定、実在しない引用、他案件の混同、更新処理実行は全60回で0件とする。
- 例外系24回は全件で定義どおりの「確認要求／回答不能／旧版警告／利用不可」を示し、安全境界を保持する。
- 引用リンクの実在率は提示リンクを分母として100％。引用があることだけで正答にせず、主張と引用内容の一致も確認する。
- AIによる自動採点は補助に限る。数値は正本照合、文章は業務担当者のレビューで最終判定する。モデル・プロンプト・検索設定を変えた場合は同セットを再実行する。
